# Crossplane 101 — Riepilogo

Ottimo lavoro. Hai finito il percorso guidato centrale del workshop. Fai un respiro — quello che hai nel tuo cluster adesso è già abbastanza per costruirci sopra piattaforme reali.

## Cosa hai costruito

| Modulo | Cosa hai adesso |
|---|---|
| Configura la CLI | La CLI di Crossplane fissata a una versione nota, Docker pronto a eseguire le function e `kubectl` puntato al cluster del workshop |
| Crea il tuo progetto | Una cartella di progetto, un `Application` di esempio e un XRD che la CLI ha derivato da esso — la tua API, definita mostrandone un esempio |
| Definisci un'Application | Una Composition che trasforma un solo `Application` in sei oggetti: un frontend e un backend, ciascuno con Deployment, Service e ConfigMap |
| Provala prima di pubblicare | Il ciclo render-e-valida — tutta la tua piattaforma esercitata sul laptop, senza coinvolgere un cluster |
| Pubblica la tua piattaforma | Un package Configuration in una registry, installato nel cluster per nome, e il tuo tile vivo sul wall |
| Modifica la tua Application | Una nuova versione del package che ha rimodellato un'applicazione in esecuzione che nessuno ha ri-applicato |

## Cosa sai adesso

Hai pubblicato un'API Kubernetes. `Application` è un kind che il tuo cluster comprende, con uno schema che hai progettato, sostenuto da una ricetta che hai scritto — e uno sviluppatore che la consuma scrive sei righe di YAML e non vede mai un Deployment.

Tre cose valgono la pena di essere portate fuori dalla stanza:

- **La CLI scrive il boilerplate.** Non hai scritto a mano un XRD né cablato una pipeline di function da zero. Hai mostrato un esempio alla CLI e lei ha derivato l'API; hai aggiunto una function come dipendenza e riempito le risorse.
- **Il ciclo è locale.** `composition render` e `resource validate` eseguono la pipeline reale contro gli schemi reali sul tuo laptop. Gran parte della vita di una Composition si svolge in quel ciclo, non in un cluster.
- **La versione è l'unità di cambiamento.** Hai modificato una ricetta, pubblicato `v0.2.0`, e un `Application` che qualcuno aveva già creato l'ha seguita. Nessuno ha modificato un oggetto vivo, e nulla è andato alla deriva tra ciò che il cluster esegue e ciò che la ricetta dice.

Quest'ultima proprietà — cambia la ricetta, ogni istanza esistente riconcilia — è il primitivo su cui è costruita ogni piattaforma Crossplane.

## Cosa non hai ancora visto

Tutto ciò che hai composto era un oggetto Kubernetes nativo. L'altra metà di Crossplane è il **Provider**: un package che gli insegna a gestire cose fuori dal cluster — release Helm, database cloud, repository, altri cluster. È la prima tappa del 2XX.

## Dove andare adesso

Il resto del workshop è choose-your-own-adventure. Scegli quello che si adatta a dove la tua coppia vuole spingersi:

| Sezione | Forma | Scegli questa se vuoi… |
|---|---|---|
| [Crossplane 2XX](../crossplane-2xx/overview) | Mix di walkthrough guidati e puntatori aperti | Imparare la CLI di Crossplane, eseguire pipeline imperative `Operation`, o interiorizzare il pattern Provider/ProviderConfig/MR prima di toccare cloud reali |
| [Crossplane 3XX](../crossplane-3xx/overview) | Task a media difficoltà guidati da puntatori | Provisionare risorse reali — un repo su GitHub, un bucket su AWS / GCP / Azure, o un database MySQL nel progetto Aruba della tua piattaforma — e impacchettare l'XRD di 101 come `Configuration` |
| [Crossplane 4XX](../crossplane-4xx/overview) | Tracce da documentazione upstream | Generare un Provider da Terraform con Upjet, o fare un vero upgrade v1→v2 |
| [Journey](../journeys/overview) | Scenari trasversali | Unire i task standalone in una storia del mondo reale — una piattaforma sviluppo interna, una landing zone cloud, o un processo automatizzato a lunga durata |

Se non sai dove andare, il default sicuro è aprire la [panoramica 2XX](../crossplane-2xx/overview) e scegliere un task `(Guided)` — quelli portano la stessa forma passo-passo dei moduli 101 che hai appena finito. Da lì, salta in 3XX quando vuoi puntare un Provider a credenziali cloud reali.

In ogni caso, il [Cheatsheet](../cheatsheet) e la pagina [Troubleshooting](../troubleshooting) sono le due tab da tenere aperte mentre esplori.
