# Running the workshop on your own laptop

The main workshop hands each pair a pre-provisioned cluster. If you want to walk through Connect-to-your-cluster and the **Crossplane 101** track on your own — outside the live workshop, with no shared infrastructure — this page is the full recipe. Everything runs in a single [k3d](https://k3d.io) cluster on your machine.

You do not need to clone a repo. Every manifest is fetched from public URLs; every image is pulled from public registries.

:::note Running on Windows?
The workshop has been tested on Mac and Ubuntu (both with Docker Desktop). On Windows, your best bet is WSL.
:::

## Prerequisites

| Tool | Install hint (macOS; on Linux, follow the tool's link) |
|---|---|
| [Docker](https://docs.docker.com/get-docker/) | `brew install --cask docker` on macOS (or better, Docker Desktop)|
| [kubectl](https://kubernetes.io/docs/tasks/tools/) | `brew install kubernetes-cli` |
| [helm](https://helm.sh/docs/intro/install/) | `brew install helm` |
| [k3d](https://k3d.io/#installation) | `brew install k3d` |

:::note Using kind or minikube instead?
This recipe assumes k3d. The package registry relies on k3d's port mapping and on k3s's default Service range, so on minikube, kind or another local cluster the registry steps need adapting.
:::

## 1. Create the cluster

```bash
k3d cluster create crossplane-workshop-solo \
  -p "8080:80@loadbalancer" \
  -p "127.0.0.1:5111:30511@server:0" \
  --k3s-arg "--disable=traefik@server:0"
```

Three flags worth explaining:
* `-p "8080:80@loadbalancer"` forwards your host's port 8080 to the cluster's ServiceLB, which is where Envoy Gateway terminates traffic.
* `-p "127.0.0.1:5111:30511@server:0"` exposes the cluster's package registry on your laptop at `127.0.0.1:5111`, and only there: nothing else on your network can reach it.
* `--k3s-arg "--disable=traefik@server:0"` turns off k3s's bundled traefik ingress controller — the workshop routes through Envoy Gateway (Gateway API), and two controllers fighting over port 80 ends with curl getting traefik's 404 page instead of the docs.

When the cluster is up, `kubectl cluster-info` should show a `k3d-crossplane-workshop-solo` context.

## 2. Install Envoy Gateway

The workshop's routing is [Gateway API](https://gateway-api.sigs.k8s.io)-native and does not use Ingress:

```bash
helm install eg oci://docker.io/envoyproxy/gateway-helm \
  --version v1.9.3 \
  --namespace envoy-gateway-system --create-namespace \
  --wait
```

## 3. Install the docs + wall + validator

One `kubectl apply` installs:
1. the Docusaurus site (this one)
2. the validator sidecar (to check inside your cluster from localhost)
3. a `Gateway` listener on port 80
4. HTTPRoutes that expose `/` → docs, `/team/local/` → the frontend you'll create in the Define-an-Application module, and `/team/local/api/` → its backend
5. a package registry (zot), where you'll push the platform you build in the Publish-your-platform module

:::note Don't trust, verify
Feel free to check the YAML before applying it. It's not long.
:::

```bash
kubectl apply -f https://raw.githubusercontent.com/ricCap/crossplane-workshop/{{REF}}/gitops/solo/all.yaml
```

Wait for the docs pod to come up:

```bash
kubectl wait --for=condition=Available deploy/docs -n docs --timeout=180s
```

## 4. Install Crossplane

The Crossplane 101 modules assume a running Crossplane. Install UXP, Upbound's distribution of Crossplane, with the same release name and values a workshop pair cluster has:

```bash
helm upgrade --install crossplane crossplane \
  --repo https://charts.upbound.io/stable \
  --version 2.4.3-up.2 --devel \
  --namespace crossplane-system --create-namespace \
  --set webui.enabled=true \
  --wait --timeout 10m
```

`--devel` is needed because Helm treats the `-up.1` suffix as a pre-release tag and skips it otherwise. Expect a minute or two while the images pull.

Then point Crossplane at the registry from step 3:

```bash
kubectl apply -f https://raw.githubusercontent.com/ricCap/crossplane-workshop/{{REF}}/gitops/solo/imageconfig.yaml
```

You push packages to `127.0.0.1:5111`, but inside the cluster that address is the pod itself. This `ImageConfig` tells Crossplane to fetch anything under `127.0.0.1:5111` from the registry's in-cluster address instead. It applies after the install because the `ImageConfig` type only exists once Crossplane is running.

## 5. Open the workshop

Visit [http://localhost:8080/](http://localhost:8080/). You should land on the same page you're reading now, served from your k3d cluster.

## 6. Do the modules

Follow Connect-to-your-cluster, then the Crossplane 101 modules, in order. Three differences from the workshop-day flow:

- **No kubeconfig download.** You're already on the cluster where the modules run — `kubectl config current-context` is `k3d-crossplane-workshop-solo`.
- **No registry login.** Your registry is `127.0.0.1:5111` and needs no credentials. Set `export REGISTRY=127.0.0.1:5111` where the workshop tells you to log in.
- **Your pair ID is `local`.** The validator reports a single synthetic pair called `local`, and the wall's tile at `/team/local/` is wired to the frontend + backend Services that the Define-an-Application module's `Application` XR creates in the `default` namespace.

Each module's validation button will evaluate against your k3d cluster and flip green as you progress.

## 7. Clean up

```bash
k3d cluster delete crossplane-workshop-solo
```

## What's intentionally missing

- **Cluster isolation.** You are both operator and participant; if you `kubectl delete ns crossplane-system`, you break your own setup. In the live workshop, each pair has their own cluster, so a mistake stays with you.
- **GitOps.** The solo path applies raw YAML. No sync loop, no self-heal — if you want changes to stick, re-apply the manifests.
- **TLS.** Traffic is plain HTTP on localhost:8080.

## Troubleshooting

**`k3d cluster create` fails with "port 8080 already allocated"**
: Another process is bound to 8080 on your host. Stop it, or pick a different host port (e.g. `-p "18080:80@loadbalancer"` and visit `http://localhost:18080/`). Use the same port in your browser.

**`k3d cluster create` fails with "port 5111 already allocated"**
: Another process holds 5111. Free it, or pick another host port, for example `-p "127.0.0.1:5112:30511@server:0"`. Then apply the `ImageConfig` with the same port, and use it in your `REGISTRY`:

  ```bash
  curl -sL https://raw.githubusercontent.com/ricCap/crossplane-workshop/{{REF}}/gitops/solo/imageconfig.yaml | sed 's/5111/5112/' | kubectl apply -f -
  export REGISTRY=127.0.0.1:5112
  ```

**`helm install eg …` fails with "cannot pull OCI chart"**
: Docker Hub rate-limits anonymous OCI pulls. Authenticate with `docker login` (any free Docker Hub account works) and retry.

**Wall shows no tiles / `/api/pairs` returns an empty array**
: The `VALIDATOR_SOLO` env var isn't set. If you applied the manifest above, this should not happen; re-check with `kubectl get deploy docs -n docs -o yaml | grep -A1 VALIDATOR_SOLO`.

**`/team/local/` returns 404 before you've finished the Define-an-Application module**
: Expected. The `frontend` and `backend` Services don't exist yet — the `Application` XR in that module creates them. Once the XR goes Ready, the route starts working with no further action on your part.
