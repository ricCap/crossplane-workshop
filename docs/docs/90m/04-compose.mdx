## 4.1 Before you start ⏱️ 3m

Your `WebApp` API exists but does nothing. A **Composition** is the recipe that says what a `WebApp` turns into — here, a Deployment and a Service.

A Composition runs a **pipeline** of functions. You generate one function that writes the two resources, and the CLI adds a second that reports when they are ready.

**Prerequisites.** You need the project from [Create your project](./create-your-project), with `apis/webapps/definition.yaml` in it.

You're about to generate the Composition, generate a function, and fill in its template.

## 4.2 Build the recipe ⏱️ 12m

### 1. Generate the Composition

```bash
crossplane composition generate apis/webapps/definition.yaml
```

```
Ensuring function-auto-ready dependency...
✓ Ensuring function-auto-ready dependency
Writing Composition...
✓ Writing Composition
```

This writes `apis/webapps/composition.yaml`, adds `function-auto-ready` to your project's dependencies, and creates a `schemas/` directory. Leave `schemas/` alone — it is generated, and it is what gives your editor autocomplete in step 4.

### 2. Generate a function to write the resources

```bash
crossplane function generate compose-webapp apis/webapps/composition.yaml --language go-templating
```

```
Generating go-templating function...
✓ Generating go-templating function
Writing function files...
✓ Writing function files
Adding pipeline step to composition...
✓ Adding pipeline step to composition
```

Open `apis/webapps/composition.yaml` and note the order: your `compose-webapp` step runs first and creates the resources, then `function-auto-ready` reports on them.

### 3. Add the Kubernetes API schemas

```bash
crossplane dependency add k8s:v1.35.0
```

```
Adding Kubernetes API v1.35.0...
✓ Adding Kubernetes API v1.35.0
```

This is what teaches your editor about `Deployment` and `Service` while you write the next step.

### 4. Fill in the template

The generator left you two files in `functions/compose-webapp/`. The first, `00-prelude.yaml.gotmpl`, already reads your `WebApp` into a variable called `$xr` — leave it as it is.

Replace the contents of `01-compose.yaml.gotmpl` with the template below. **Three values are missing**, marked `FILL ME IN`. Each one comes from the `WebApp` you wrote in the last module, through `$xr`.

```yaml
# code: language=yaml
# yaml-language-server: $schema=../../schemas/json/index.schema.json
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ $xr.metadata.name }}
  namespace: {{ $xr.metadata.namespace }}
  annotations:
    {{ setResourceNameAnnotation "deployment" }}
spec:
  replicas: FILL ME IN
  selector:
    matchLabels:
      app: {{ $xr.metadata.name }}
  template:
    metadata:
      labels:
        app: {{ $xr.metadata.name }}
    spec:
      containers:
        - name: app
          image: FILL ME IN
          ports:
            - containerPort: 9898
---
apiVersion: v1
kind: Service
metadata:
  name: {{ $xr.metadata.name }}
  namespace: FILL ME IN
  annotations:
    {{ setResourceNameAnnotation "service" }}
spec:
  selector:
    app: {{ $xr.metadata.name }}
  ports:
    - port: 80
      targetPort: 9898
```

The fields you defined on the API in the last module are `$xr.spec.image` and `$xr.spec.replicas`. The namespace is `$xr.metadata.namespace`, the same expression the Deployment already uses.

`setResourceNameAnnotation` gives each resource a stable name inside the Composition, so Crossplane updates them instead of recreating them.

## 4.3 What just happened

You wrote the recipe that turns one `WebApp` into two Kubernetes objects, and you never had to write the Composition's plumbing by hand — the CLI generated it from the API you designed.

The template is only text until something runs it. That's the next module, and it happens entirely on your laptop.
