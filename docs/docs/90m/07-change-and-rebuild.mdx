## 7.1 Before you start ⏱️ 2m

A platform API is only useful if you can change it after people depend on it. You ship a new version of the package, and every `WebApp` already in the cluster picks up the change.

The one thing to know is where your template lives. It is baked into the **function image**, not into the Composition — so editing it produces a new function image, and that is what you ship.

**Prerequisites.** You need the installed package from [Package and ship](./package-and-ship), with `podinfo` running.

You're about to change the recipe, publish a new version, and watch a resource you already created follow it.

## 7.2 Ship a change ⏱️ 5m

### 1. Change the template

In `functions/compose-webapp/01-compose.yaml.gotmpl`, change the Service port from `80` to `8080`:

```yaml
  ports:
    - port: 8080
      targetPort: 9898
```

### 2. Build and push a new version

```bash
crossplane project build
crossplane project push -t v0.2.0
```

Use a new tag. Pushing a changed package over an existing tag leaves the cluster with no reason to pull it again.

### 3. Point the cluster at the new version

```bash
kubectl patch configuration.pkg local-my-platform --type=merge \
  -p '{"spec":{"package":"<your registry>/<your pair ID>/my-platform:v0.2.0"}}'
```

Now watch it, and expect it to stall:

```bash
kubectl get configuration.pkg
```

```
NAME                INSTALLED   HEALTHY   PACKAGE
local-my-platform   True        False     .../my-platform:v0.2.0
```

### 4. Clear the pinned dependency

`HEALTHY` stays `False`. Ask why:

```bash
kubectl get configuration.pkg local-my-platform \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.message}{"\n"}{end}'
```

```
Healthy=False cannot resolve package dependencies: existing package
.../my-platform_compose-webapp@sha256:bdc1aaf... is incompatible with
constraint sha256:843d023...
```

Your new Configuration wants the function image you built in step 2, but the Function already in the cluster is pinned to the **old image digest**, and the two cannot both be satisfied. Delete the Function; the Configuration recreates it at the digest it wants:

```bash
kubectl delete function.pkg local-my-platformcompose-webapp
```

```bash
kubectl get configuration.pkg
```

```
NAME                INSTALLED   HEALTHY   PACKAGE
local-my-platform   True        True      .../my-platform:v0.2.0
```

### 5. Watch the change land

You have not touched the `WebApp`. Crossplane reconciles it against the new recipe on its own:

```bash
kubectl get svc podinfo -n default
```

```
NAME      TYPE        CLUSTER-IP     PORT(S)    AGE
podinfo   ClusterIP   10.43.57.173   8080/TCP   7m25s
```

Same Service, same cluster IP, new port. It was updated in place, not replaced — which is what the `setResourceNameAnnotation` in your template buys you.

## 7.3 What just happened

You changed one template, shipped it as a version, and a resource somebody had already created moved to the new shape without being touched. That is the difference between a platform API and a pile of YAML: the recipe is versioned, and consumers follow it.

The digest conflict in step 4 is worth remembering. Package dependencies are pinned by digest, so a dependency that changed underneath a package has to be cleared before the new version can resolve.
