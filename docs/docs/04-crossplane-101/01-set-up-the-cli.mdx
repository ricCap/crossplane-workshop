## 1.1 Before you start ⏱️ 1m

The Crossplane CLI is a single binary. It does the work you would otherwise do by hand: it scaffolds a project, generates the API and Composition files, renders them locally, and packages them for your cluster.

Every command group this workshop uses — `project`, `xrd`, `function`, `dependency` and `resource` — is marked beta. You pin a version so you get the output this workshop shows.

You're about to check Docker, install the CLI, log in to the workshop registry, and confirm your cluster is running Crossplane.

## 1.2 Install and log in ⏱️ 4m

### 1. Check Docker

```bash
docker version
```

Both a `Client` and a `Server` section should print. If `Server` is missing, start your container runtime and run the command again.

### 2. Install the CLI

```bash
curl -sfL "https://cli.crossplane.io/install.sh" | XP_VERSION=v2.5.0 sh
sudo mv crossplane /usr/local/bin/
crossplane version --client
```

The last command prints the pinned version:

```
Client Version: v2.5.0
```

The installer downloads the binary into the current directory and does not add it to your `PATH`, which is why the `mv` is needed.

Keep the `--client` flag. Plain `crossplane version` also asks the cluster which version it runs, and fails with `unable to get crossplane version` until your `kubectl` context is set in step 4.

### 3. Log in to the registry

Your credentials bundle has a registry address and a login. Export them and log in:

```bash
export REGISTRY=<registry address from your bundle>
docker login "$REGISTRY"
```

### 4. Point `kubectl` at your workshop cluster

```bash
export KUBECONFIG=<path to the kubeconfig from your bundle>
kubectl get namespaces
```

You should see a list of namespaces.

### 5. Check Crossplane is running

Your cluster needs Crossplane before it can accept the package you build in [Publish your platform](./package-and-ship).

```bash
kubectl get pods -n crossplane-system
```

If Crossplane is running, you get pods in `Running`:

```
NAME                                       READY   STATUS    RESTARTS   AGE
crossplane-58ff757f44-5vjxz                1/1     Running   0          4h
crossplane-apollo-7d475f549f-bbd6s         3/3     Running   1          4h
crossplane-rbac-manager-75f69f7d64-7xttd   1/1     Running   0          4h
upbound-controller-manager-85cd77fb9-rk2jw 1/1     Running   0          4h
webui-5c65cc8bdf-9wtzn                     1/1     Running   0          4h
```

Two of those five are the ones you'll interact with. **`crossplane`** is the core controller — the long-running program that watches XRDs, Compositions, XRs and Functions and runs a reconciliation loop on each. Every module after this one depends on that Pod being healthy. **`webui`** is UXP's read-only dashboard, handy for inspecting what you compose without `kubectl`. The other three are infrastructure you won't touch.

If instead you get `No resources found in crossplane-system namespace`, install it:

<details>
<summary>Crossplane isn't running — install it (⏱️ ~5m)</summary>

Add the Upbound Helm repo:

```bash
helm repo add upbound-stable https://charts.upbound.io/stable
helm repo update upbound-stable
```

Install UXP into `crossplane-system`:

```bash
helm install crossplane upbound-stable/crossplane \
  --version 2.2.0-up.5 \
  --namespace crossplane-system \
  --create-namespace \
  --devel \
  --wait \
  --set webui.enabled=true
```

Four flags are doing real work:

- `--version 2.2.0-up.5` pins the chart. Without it Helm takes the newest available, which has drifted past what these modules were written against.
- `--devel` is required to install that version at all — the `-up.5` suffix is a SemVer pre-release tag, and Helm filters those out by default.
- `--wait` blocks until the Crossplane Deployments report Available, so the command only returns once the cluster is actually ready. Expect 30–60 seconds on a workshop-sized cluster.
- `--set webui.enabled=true` turns on the read-only Web UI.

This installs **UXP**, Upbound's distribution of Crossplane: the same core, plus the bundled Web UI. Everything in this workshop transfers to upstream Crossplane one for one — see the [Cheatsheet](../cheatsheet) for the difference.

Then re-run the check above and wait for `Running`.

</details>

## 1.3 What just happened

You have the tools to build a platform API: the CLI to author and package it, Docker to run it locally, a registry to publish it to, and a cluster running Crossplane to install it into.
