## 2.1 Before you start ⏱️ 5m

A Crossplane project is a folder holding everything you publish: your API definition, the Composition that implements it, any functions, examples and tests. `crossplane project init` creates it, and `crossplane-project.yaml` records where the finished package gets published.

The one concept to take from this module is the **XRD**, the composite resource definition. It defines the API you offer other teams. You will not write one by hand — you write an example of the object someone would apply, and the CLI derives the API from it.

You're about to create the project, write an example `Application`, and generate its API.

### The words you'll see ⏱️ 2m

Five terms turn up across the next four modules. Treat this as the glossary; the fuller version, including the pieces you meet in 2XX, lives in the [Cheatsheet](../cheatsheet#core-objects).

| Component | What it is | Object scope | Scope of the kind it defines / produces |
|---|---|---|---|
| **CRD** (Kubernetes) | Custom Resource Definition. Extends the API server with a new kind. You won't write one — Crossplane generates it for you from your XRD | Cluster | `Namespaced` or `Cluster`, per the CRD's `spec.scope` |
| **XRD** (Composite Resource Definition) | Declares the schema of a new Crossplane API: what fields it has, what types. Applying it makes Crossplane create the matching CRD. This is what `xrd generate` writes | Cluster | `Namespaced` (v2 default), `Cluster`, or `LegacyCluster`, per the XRD's `spec.scope` |
| **XR** (Composite Resource) | An instance of an XRD. Apply one and the Composition runs. Your `examples/applications/hello.yaml` is one | Per the XRD — `Namespaced` for the `Application` you're defining | — |
| **Composition** | The recipe. "When someone creates this kind of XR, produce these resources." The next module writes it | Cluster | — |
| **Composition function** | Pluggable logic the Composition's pipeline runs to produce desired state. You'll use `function-patch-and-transform`, recorded as a dependency of your package rather than installed by hand | Cluster (it's a Crossplane package) | — |

The split that matters: **XRD and Composition are yours**, the platform team's, applied once. **The XR is what a user applies**, once per request. In this hour you wear both hats; on a real platform they are different teams.

## 2.2 Scaffold the project ⏱️ 8m

### 1. Initialize the project

```bash
export PAIR=<your pair ID>
crossplane project init my-platform --registry "$REGISTRY/$PAIR"
cd my-platform
ls
```

```
apis
crossplane-project.yaml
examples
functions
operations
tests
```

`crossplane-project.yaml` records where your package gets published. The `--registry` value you passed became its `spec.repository`:

```yaml
spec:
  repository: <your registry>/<your pair ID>/my-platform
```

### 2. Write an example of the object other teams will apply

This is your platform's product: one short file that asks for an application, with none of the Deployments, Services or ConfigMaps that make it real.

```bash
mkdir -p examples/applications
cat <<'EOF' > examples/applications/hello.yaml
apiVersion: workshop.example.io/v1alpha1
kind: Application
metadata:
  name: hello
  namespace: default
spec:
  message: "Hello from our platform"
  theme: ocean
EOF
```

Two fields, and both are choices *you* are making on behalf of every team that will use this API: what they can say, and how it looks.

### 3. Generate the API from the example

```bash
crossplane xrd generate examples/applications/hello.yaml --from xr
```

```
Created CompositeResourceDefinition (XRD) at applications/definition.yaml
```

That path is relative to `apis/`, so the file is at `apis/applications/definition.yaml`. Open it and find the two fields the CLI inferred from your example:

```yaml
message:
  type: string
theme:
  type: string
```

The CLI reads shapes, not intent. It saw two strings and wrote two strings — it has no way to know that `message` is mandatory, or that `theme` is a short list rather than any text at all. Those are decisions you add by hand once the shape is right, and `apis/applications/definition.yaml` is now yours to edit.

### 4. Add the intent the CLI could not infer ⏱️ 1m

In `apis/applications/definition.yaml`, replace the `spec:` block with this one:

```yaml
          spec:
            description: ApplicationSpec defines the desired state of Application.
            properties:
              message:
                type: string
              theme:
                type: string
                enum: [ocean, sunset, forest, ember, violet]
                default: ocean
            required:
              - message
            type: object
```

Three additions, each one a decision about what your API will and will not accept:

- **`message` is required.** There is no sensible default for what somebody else's application should say.
- **`theme` is an `enum` with a `default`.** The workshop wall maps each name to a palette, so the set is closed. Make it a free string and a typo produces an unstyled tile that looks like a bug in your platform; make it an enum and the API server rejects the typo at `kubectl apply`, with the valid options in the error.
This is the line between a schema that *describes* a field and one that *constrains* it. Everything above is enforced by the Kubernetes API server before your Composition ever runs.

## 2.3 What just happened

You defined an API by showing one example of it, then tightened it into something you would be willing to put in front of another team. `Application` is now a kind your cluster could offer, with a schema derived from a file a developer could have written and constraints you chose deliberately.

Nothing yet says what an `Application` *becomes*. That's the next module.
