## 6.1 Before you start ⏱️ 2m

A platform API is only useful if you can change it after people depend on it. You publish a new version of the package, and every `Application` already running picks the change up.

Nobody re-applies anything. The consumers' files do not change at all.

**Prerequisites.** You need the installed package from [Publish your platform](./package-and-ship), with your tile live.

You're about to change the recipe, publish a new version, and watch a resource you already created follow it.

## 6.2 Ship a change ⏱️ 7m

### 1. Change the recipe

In `apis/applications/composition.yaml`, find the backend ConfigMap's `CombineFromComposite` patch and add a marker to the message template:

```yaml
                    fmt: '{"message":"%v ✨","theme":"%v","replicas":%v}'
```

This is a platform-side change. No `Application` anywhere knows about it — you edited the recipe, not anybody's resource.

### 2. Build and push a new version

```bash
crossplane project build
crossplane project push -t v0.2.0
```

Use a new tag. Pushing changed content over an existing tag leaves the cluster with no reason to pull it again.

### 3. Point the cluster at the new version

```bash
kubectl patch configuration.pkg local-my-platform --type=merge \
  -p '{"spec":{"package":"<your registry>/<your pair ID>/my-platform:v0.2.0"}}'
```

```bash
kubectl get configuration.pkg
```

```
NAME                INSTALLED   HEALTHY   PACKAGE
local-my-platform   True        True      .../my-platform:v0.2.0
```

### 4. Watch the change land

You have not touched the `Application`. Crossplane reconciles it against the new recipe on its own:

```bash
kubectl get configmap backend -n default -o jsonpath='{.data.message}'
```

```
{"message":"Hello from our platform ✨","theme":"ocean","replicas":1}
```

Your tile on the workshop wall picks the change up on its own within a few seconds, and pulses to say so. Nobody reloaded anything.

Give it a few seconds. The ConfigMap updates almost immediately, but the copy projected
into the running Pod only refreshes on the kubelet's sync — usually seconds, occasionally
up to a minute. If you would rather not wait:

```bash
kubectl rollout restart deployment backend
```

The ConfigMap was updated in place, not replaced — which is what the resource names in your recipe buy you. Crossplane matched each composed resource to the one already there and patched the difference.

### 5. The other kind of change

Everything above was your change, as the platform team. This one belongs to the consumer:

```bash
kubectl patch application hello -n default --type=merge -p '{"spec":{"replicas":3}}'
```

Watch the replica dots on your tile fill in as the pods come up. The recipe did not change at all this time — the same Composition produced a different result, because the `Application` asked for something different.

Two changes, two owners, one API. That is the split from [Create your project](./create-your-project) made concrete: the XRD and the Composition are the platform's, the XR is the user's, and neither side has to coordinate with the other to move.

## 6.3 What just happened

You changed one file, published it as a version, and an application somebody had already created moved to the new shape without being touched. That is the difference between a platform API and a pile of YAML: the recipe is versioned, and every consumer follows it.

Notice what you did *not* have to do. No editing live objects, no telling anyone to re-apply, no drift between what the cluster runs and what the recipe says.

Then you changed the same application from the other side, as its owner, and got a different result out of the same recipe. Both changes reconciled the same way, which is the point: Crossplane does not care whether the new desired state came from the platform or from the user.

### Go deeper

- **Stretch: add a field.** Add `subtitle` to the XRD (with a default), patch it through the
  Composition into a new ConfigMap key, and apply a fresh `Application` that sets it. Good
  sandbox if your pair finishes early.
- [Composition revisions](https://docs.crossplane.io/latest/concepts/composition-revisions/) — how Crossplane keeps old Compositions around so existing XRs stay stable while new ones pick up the new recipe.
- [Composition functions catalogue](https://github.com/crossplane-contrib) — `function-kcl`, `function-go-templating`, `function-auto-ready`: patterns for moving beyond patch-and-transform once you need more logic.
