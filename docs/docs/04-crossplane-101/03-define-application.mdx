## 3.1 Before you start ⏱️ 3m

Your `Application` API exists but produces nothing. A **Composition** is the recipe that says what an `Application` turns into — here, a frontend and a backend, each with a Deployment, a Service and a ConfigMap.

A Composition runs a **pipeline** of functions. You will use `function-patch-and-transform`, which takes a list of resources to create and lets you patch values from the XR into them.

**Prerequisites.** You need the project from [Create your project](./create-your-project), with `apis/applications/definition.yaml` in it.

You're about to generate the Composition, add the function it needs, and fill in the six resources an `Application` becomes.

## 3.2 Write the recipe ⏱️ 15m

### 1. Generate the Composition

```bash
crossplane composition generate apis/applications/definition.yaml
```

```
Ensuring function-auto-ready dependency...
✓ Ensuring function-auto-ready dependency
Writing Composition...
✓ Writing Composition
```

This writes `apis/applications/composition.yaml`, adds `function-auto-ready` to your project's dependencies, and creates a `schemas/` directory. Leave `schemas/` alone — it is generated, and it is what gives your editor autocomplete in step 3.

### 2. Add the function that builds the resources

```bash
crossplane dependency add xpkg.crossplane.io/crossplane-contrib/function-patch-and-transform
```

The generated Composition only has `function-auto-ready`, which reports on resources but creates none. `function-patch-and-transform` is the one that makes them.

### 3. Fill in the recipe

Replace `apis/applications/composition.yaml` with the following. It is long, but it is six variations on one idea: a resource to create, and the patches that pull values out of the `Application`.

```yaml
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: applications.workshop.example.io
spec:
  compositeTypeRef:
    apiVersion: workshop.example.io/v1alpha1
    kind: Application
  mode: Pipeline
  pipeline:
    - step: crossplane-contrib-function-patch-and-transform
      functionRef:
        name: crossplane-contrib-function-patch-and-transform
      input:
        apiVersion: pt.fn.crossplane.io/v1beta1
        kind: Resources
        resources:
          - name: frontend-configmap
            base:
              apiVersion: v1
              kind: ConfigMap
              metadata:
                name: frontend
                namespace: default
              data:
                index.html: |
                  <!DOCTYPE html>
                  <html><head><meta charset="utf-8"><title>Tile</title>
                  <style>
                    body { font-family: sans-serif; margin: 0; padding: 20px; text-align: center; }
                    #title { font-size: 2rem; font-weight: 700; }
                    .dot { display: inline-block; width: 10px; height: 10px; border-radius: 50%; margin: 0 3px; }
                  </style>
                  </head><body>
                  <div id="title">Loading...</div>
                  <div id="dots"></div>
                  <script>
                    const THEMES = { ocean: '#0ea5e9', sunset: '#f97316', forest: '#16a34a', ember: '#dc2626', violet: '#7c3aed' };
                    fetch('./api/message')
                      .then(r => r.text())
                      .then(txt => {
                        try {
                          const d = JSON.parse(txt);
                          const accent = THEMES[d.theme] || '#64748b';
                          const el = document.getElementById('title');
                          el.innerText = d.message || '(no message)';
                          el.style.color = accent;
                          document.getElementById('dots').innerHTML = Array.from(
                            { length: Number(d.replicas) || 1 },
                            () => '<span class="dot" style="background:' + accent + '"></span>'
                          ).join('');
                        } catch (e) {
                          document.getElementById('title').innerText = 'Bad response: ' + txt;
                        }
                      })
                      .catch(e => {
                        document.getElementById('title').innerText = 'Error: ' + e.message;
                      });
                  </script>
                  </body></html>
            readinessChecks:
              - type: None
          - name: frontend-deployment
            base:
              apiVersion: apps/v1
              kind: Deployment
              metadata:
                name: frontend
                namespace: default
              spec:
                replicas: 1
                selector:
                  matchLabels: { app: frontend }
                template:
                  metadata:
                    labels: { app: frontend }
                  spec:
                    containers:
                      - name: nginx
                        image: public.ecr.aws/docker/library/nginx:alpine
                        ports:
                          - containerPort: 80
                        volumeMounts:
                          - name: html
                            mountPath: /usr/share/nginx/html
                    volumes:
                      - name: html
                        configMap:
                          name: frontend
            readinessChecks:
              - type: MatchCondition
                matchCondition:
                  type: Available
                  status: "True"
            patches:
              - type: FromCompositeFieldPath
                fromFieldPath: spec.replicas
                toFieldPath: spec.replicas
          - name: frontend-service
            base:
              apiVersion: v1
              kind: Service
              metadata:
                name: frontend
                namespace: default
              spec:
                selector: { app: frontend }
                ports:
                  - port: 80
                    targetPort: 80
            readinessChecks:
              - type: None
          - name: backend-configmap
            base:
              apiVersion: v1
              kind: ConfigMap
              metadata:
                name: backend
                namespace: default
              data:
                message: '{"message":"placeholder","theme":"ocean","replicas":1}'
            readinessChecks:
              - type: None
            patches:
              - type: CombineFromComposite
                combine:
                  variables:
                    - fromFieldPath: spec.message
                    - fromFieldPath: spec.theme
                    - fromFieldPath: spec.replicas
                  strategy: string
                  string:
                    fmt: '{"message":"%v","theme":"%v","replicas":%v}'
                toFieldPath: data.message
          - name: backend-deployment
            base:
              apiVersion: apps/v1
              kind: Deployment
              metadata:
                name: backend
                namespace: default
              spec:
                replicas: 1
                selector:
                  matchLabels: { app: backend }
                template:
                  metadata:
                    labels: { app: backend }
                  spec:
                    containers:
                      - name: nginx
                        image: public.ecr.aws/docker/library/nginx:alpine
                        ports:
                          - containerPort: 80
                        volumeMounts:
                          - name: api
                            mountPath: /usr/share/nginx/html/api
                    volumes:
                      - name: api
                        configMap:
                          name: backend
            readinessChecks:

            readinessChecks:
```

<summary>Walk through the recipe, resource by resource</summary>

The Composition is one Kubernetes resource with a long body. Each block below is one piece of the file you just pasted, with what it does and why it looks like that.

#### The wrapper

```yaml
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: applications.workshop.example.io
spec:
  compositeTypeRef:
    apiVersion: workshop.example.io/v1alpha1
    kind: Application
  mode: Pipeline
  pipeline:
    - step: crossplane-contrib-function-patch-and-transform
      functionRef:
        name: crossplane-contrib-function-patch-and-transform
      input:
        apiVersion: pt.fn.crossplane.io/v1beta1
        kind: Resources
        resources:
          # one entry per composed resource — see below
```

`compositeTypeRef` binds this Composition to the `Application` XRD the CLI generated for you — when an `Application` XR is created, Crossplane finds this Composition by matching that ref. `mode: Pipeline` tells Crossplane to call functions in order; this Composition's pipeline has one step that hands the `resources` list below to the patch-and-transform function you added as a dependency.

#### `frontend-configmap` — the static HTML

```yaml
- name: frontend-configmap
  base:
    apiVersion: v1
    kind: ConfigMap
    metadata:
      name: frontend
      namespace: default
    data:
      index.html: |
        <!DOCTYPE html>
        <html><head><meta charset="utf-8"><title>Tile</title>
        <style>
          body { font-family: sans-serif; margin: 0; padding: 20px; text-align: center; }
          #title { font-size: 2rem; font-weight: 700; }
          .dot { display: inline-block; width: 10px; height: 10px; border-radius: 50%; margin: 0 3px; }
        </style>
        </head><body>
        <div id="title">Loading...</div>
        <div id="dots"></div>
        <script>
          const THEMES = { ocean: '#0ea5e9', sunset: '#f97316', forest: '#16a34a', ember: '#dc2626', violet: '#7c3aed' };
          fetch('./api/message')
            .then(r => r.text())
            .then(txt => {
              try {
                const d = JSON.parse(txt);
                const accent = THEMES[d.theme] || '#64748b';
                const el = document.getElementById('title');
                el.innerText = d.message || '(no message)';
                el.style.color = accent;
                document.getElementById('dots').innerHTML = Array.from(
                  { length: Number(d.replicas) || 1 },
                  () => '<span class="dot" style="background:' + accent + '"></span>'
                ).join('');
              } catch (e) {
                document.getElementById('title').innerText = 'Bad response: ' + txt;
              }
            })
            .catch(e => {
              document.getElementById('title').innerText = 'Error: ' + e.message;
            });
        </script>
        </body></html>
  readinessChecks:
    - type: None
```

The page's `<script>` fetches `./api/message`, parses the JSON, writes the `message` into the tile, colours it from the `theme` name, and draws one dot per replica. Every `Application` ships the same HTML — no patch needed, because the values it renders arrive over HTTP from the backend rather than being baked in here.

Note that the palette lives in this page, not in the API. `theme` carries a *name*; what `ocean` looks like is a rendering decision. That is why the XRD could close the set with an `enum` without ever committing your API to a hex code.

`readinessChecks: type: None` is the right choice for ConfigMaps because they expose no Ready condition. Crossplane treats them as Ready as soon as it observes them.

#### `frontend-deployment` — the nginx that serves it

```yaml
- name: frontend-deployment
  base:
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: frontend
      namespace: default
    spec:
      replicas: 1
      selector:
        matchLabels: { app: frontend }
      template:
        metadata:
          labels: { app: frontend }
        spec:
          containers:
            - name: nginx
              image: public.ecr.aws/docker/library/nginx:alpine
              ports:
                - containerPort: 80
              volumeMounts:
                - name: html
                  mountPath: /usr/share/nginx/html
          volumes:
            - name: html
              configMap:
                name: frontend
  readinessChecks:
    - type: MatchCondition
      matchCondition:
        type: Available
        status: "True"
  patches:
    - type: FromCompositeFieldPath
      fromFieldPath: spec.replicas
      toFieldPath: spec.replicas
```

One pod running `nginx:alpine` with the ConfigMap above mounted at `/usr/share/nginx/html` — or more than one, because `spec.replicas` from the XR is patched straight onto the Deployment's own `spec.replicas`. Both fields have the same name and the same meaning, so this is the simplest patch in the file: `FromCompositeFieldPath` copies one value to one path, no formatting involved.

`type: MatchCondition` waits for `Available=True` on the Deployment — Crossplane only marks the XR Ready once both Deployments report this.

#### `frontend-service` — the in-cluster endpoint

```yaml
- name: frontend-service
  base:
    apiVersion: v1
    kind: Service
    metadata:
      name: frontend
      namespace: default
    spec:
      selector: { app: frontend }
      ports:
        - port: 80
          targetPort: 80
  readinessChecks:
    - type: None
```

Cluster-internal Service on port 80, selected by `app: frontend`. The workshop's HTTPRoute resolves `/team/<pair>/` to this Service.

#### `backend-configmap` — the only resource that reads the XR

```yaml
- name: backend-configmap
  base:
    apiVersion: v1
    kind: ConfigMap
    metadata:
      name: backend
      namespace: default
    data:
      message: '{"message":"placeholder","theme":"ocean","replicas":1}'
  readinessChecks:
    - type: None
  patches:
    - type: CombineFromComposite
      combine:
        variables:
          - fromFieldPath: spec.message
          - fromFieldPath: spec.theme
          - fromFieldPath: spec.replicas
        strategy: string
        string:
          fmt: '{"message":"%v","theme":"%v","replicas":%v}'
      toFieldPath: data.message
```

This is the interesting one. The patch's `CombineFromComposite` reads `spec.message`, `spec.theme` and `spec.replicas` from the XR, fills them into the `printf`-style template, and writes the result into `data.message` — so the ConfigMap that started as a hard-coded `"placeholder"` ends up holding the JSON the XR asked for.

**The verb is `%v`, not `%s`.** `replicas` is a number, and `%s` on a number does not fail — it quietly produces the literal text `%!s(float64=3)`, which makes the whole file invalid JSON and leaves your tile showing `Bad response:`. `%v` formats whatever it is given, so one verb covers both the strings and the number. Note too that `replicas` is the one value *not* wrapped in quotes in the template, because it should land in the JSON as a number.

`toFieldPath` is a path inside the naked `ConfigMap` body. Compare to module 4's `Object`-MR shape, which would have prefixed it with `spec.forProvider.manifest.data.message`; here the composed resource *is* the ConfigMap, so there is no MR envelope to step through.

#### `backend-deployment` — nginx as the API

```yaml
- name: backend-deployment
  base:
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: backend
      namespace: default
    spec:
      replicas: 1
      selector:
        matchLabels: { app: backend }
      template:
        metadata:
          labels: { app: backend }
        spec:
          containers:
            - name: nginx
              image: public.ecr.aws/docker/library/nginx:alpine
              ports:
                - containerPort: 80
              volumeMounts:
                - name: api
                  mountPath: /usr/share/nginx/html/api

            - name: api
              configMap:
                name: backend

    - type: MatchCondition
      matchCondition:
        type: Available
        status: "True"
```

Same shape as `frontend-deployment`, but the volume mounts at `/usr/share/nginx/html/api/`. There is no application server in this stack — the file at `/api/message` *is* the ConfigMap's `data.message`, served verbatim.

#### `backend-service` — the API endpoint

```yaml
- name: backend-service
  base:
    apiVersion: v1
    kind: Service
    metadata:
      name: backend
      namespace: default
    spec:
      selector: { app: backend }
      ports:
        - port: 5678
          targetPort: 80
  readinessChecks:
    - type: None
```

Port 5678 forwards to nginx on `targetPort: 80`. The HTTPRoute resolves `/team/<pair>/api/` to this Service.

</details>

Three things worth looking at before moving on:

- **The Services are named `frontend` and `backend`, on ports 80 and 5678.** Your workshop cluster routes `/team/<your pair ID>/` to the first and `/team/<your pair ID>/api/` to the second, by those exact names and ports. Rename them and your tile stops working.
- **`fromFieldPath: spec.message`** is how a value on the `Application` reaches the HTML the frontend serves. That one line is the whole point of the API: the developer sets `message`, and the platform decides what that means.
- **The three XR fields take two different routes.** `message` and `theme` are combined into the backend's JSON, which the page fetches at runtime. `replicas` goes somewhere else entirely — onto the frontend Deployment — because it is not something to display, it is something to *run*. One API, two kinds of consequence.
- **`readinessChecks: - type: None`** tells `function-auto-ready` not to wait on resources that have no meaningful ready condition.

### A note on RBAC ⏱️ 2m

One Kubernetes truth worth surfacing before you move on, because it decides what you're allowed to compose.

Crossplane core is what applies the resources your Composition emits. Like every controller, it can only create kinds it holds RBAC for. UXP's bundled `crossplane` ClusterRole already grants the verbs you need on the three kinds in this recipe, so the flow works without you touching RBAC at all. If your cluster is reachable, confirm it:

```bash
kubectl auth can-i create configmaps \
  --as=system:serviceaccount:crossplane-system:crossplane \
  -n default
```

```
yes
```

Two reasons it matters anyway:

- **Compose a different kind and you have to extend the grant.** The pattern is an *aggregated* `ClusterRole` carrying the label `rbac.crossplane.io/aggregate-to-crossplane: "true"` — Kubernetes' RBAC aggregator merges its rules into the existing `crossplane` ClusterRole at runtime, so you never edit the chart's role. This recipe stays inside ConfigMap, Service and Deployment, so you don't need one. A Composition that produced a `Job` would.
- **Production RBAC is narrower than this.** A broad wildcard grant is fine on a workshop cluster. In production you'd scope it down to explicit verbs on the kinds your platform actually composes, and review it the way you'd review any other privileged ServiceAccount.

This is a trade-off Crossplane v2 makes visible. The resources here are applied by Crossplane core itself, so the grant is Crossplane's. Compose through a provider instead — `provider-kubernetes`, say — and the equivalent grant moves to *that provider's* ServiceAccount via its `ProviderConfig`: the same question, one layer further away.
