## 4.1 Before you start ⏱️ 2m

You can run your Composition without a cluster. `composition render` executes the function pipeline on your laptop and prints exactly what Crossplane would create.

This is the loop you stay in while writing a Composition: edit the recipe, render, read the output. No pushing, no installing, no waiting for a controller to catch up.

**Prerequisites.** You need the Composition from [Define an Application](./define-application). Docker must be running — the CLI executes each function as a container.

You're about to render your Composition and validate the result.

## 4.2 Render and validate ⏱️ 6m

### 1. Render the Composition

```bash
crossplane composition render examples/applications/hello.yaml apis/applications/composition.yaml
```

You get the composite resource followed by the six resources your recipe produces:

```
kind: Application      name: hello
kind: ConfigMap        name: backend
kind: Deployment       name: backend
kind: Service          name: backend     port: 5678
kind: ConfigMap        name: frontend
kind: Deployment       name: frontend
kind: Service          name: frontend    port: 80
```

Check the **backend** ConfigMap — that is where your fields land:

```
message: '{"message":"Hello from our platform","theme":"ocean","replicas":1}'
```

All three values from your example `Application` are in there. That is the patch doing its job — fields on your API reaching a file inside a container. The frontend ConfigMap holds only static HTML; it fetches that JSON at runtime, which is why your message is not in it.

Check the frontend **Deployment** too: `spec.replicas` is whatever your example asked for, because that field took the other route.

Change `message` in `examples/applications/hello.yaml`, render again, and watch the output follow. That round trip is a couple of seconds, against the minutes a cluster round trip costs.

:::warning Render does not apply your defaults
`composition render` runs the function pipeline, not the Kubernetes API server — so the `default` values you put in the XRD are **not** filled in here. Leave `replicas` out of your example and `CombineFromComposite` is skipped in silence, taking `message` and `theme` with it: the backend ConfigMap keeps its hard-coded `placeholder`. A combine patch needs every variable it names.

On a real cluster the API server defaults the field before Crossplane ever sees the XR, so this only bites while rendering locally. If a render shows `placeholder` where you expected your message, a missing field is the first thing to check.
:::

### 2. Validate what you rendered

Rendering proves your recipe produces YAML. It does not prove the YAML is valid Kubernetes.

```bash
crossplane composition render examples/applications/hello.yaml apis/applications/composition.yaml -x > rendered.yaml
crossplane resource validate apis/ rendered.yaml
```

Note the `-x`. By default `render` prints only the XR's `status` and name, not its `spec` — fine for reading, but `validate` then sees an `Application` with no `message` and rejects it against your own XRD, which marks `message` required. `-x` includes the full spec, so the XR is checked as it actually is.

```
[✓] v1, Kind=ConfigMap, frontend validated successfully
[✓] apps/v1, Kind=Deployment, frontend validated successfully
[✓] v1, Kind=Service, frontend validated successfully
Total 7 resources: 0 missing schemas, 7 success cases, 0 failure cases
```

The first argument says where the schemas come from, the second says what to check. The first run downloads the Crossplane schema image, so give it a moment.

To see it catch something, misspell a field in your recipe — change `replicas:` to `replicaz:` on the frontend Deployment — then render and validate again:

```
[x] schema validation error apps/v1, Kind=Deployment, frontend : unknown field "spec.replicaz"
```

Note the render still succeeded. The pipeline produces YAML and has no idea what a Deployment is, which is exactly why validate exists. Put the field back before moving on.

## 4.3 What just happened

You ran your platform API end to end without a cluster. An `Application` went in, six Kubernetes objects came out, and all of them were checked against the real schemas.
